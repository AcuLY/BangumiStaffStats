# contracts-partners-api Specification

## Purpose
Define the isolated closed `POST /partners` wire for scope-safe source and candidate inputs and complete summary, leader, item, pagination, metadata, and personal-only collection outputs.
## Requirements
### Requirement: Partners wire SHALL be closed and scope-safe

`POST /api/v1/partners` SHALL accept a closed document containing `query`,
`input.source.personId`, a non-empty ordered-unique
`input.source.positionKeys`, optional `input.candidatePositionKey`, and optional
view. Source and candidate position keys SHALL belong to the effective query
and SHALL be treated as opaque catalog identities. Every undeclared member
SHALL be rejected.

Success SHALL return workUnit, source identity/metrics, complete summary with
fixed leaders, current items, pagination, request metadata, and personal-only
collection metadata. Global variants SHALL structurally omit all preference and
collection members.

#### Scenario: Candidate filter is omitted
- **WHEN** no candidatePositionKey is submitted
- **THEN** candidates from every query position SHALL be eligible without an `"all"` sentinel

#### Scenario: Global partner is returned
- **WHEN** a global request succeeds
- **THEN** preference and collection fields SHALL be absent rather than null

### Requirement: Partners generation SHALL be isolated

Go and TypeScript generation SHALL project only `/partners` plus transitive
schemas, use fixed capability-owned operation metadata, and emit a reproducible
projection hash. Unrelated paths and shared authority descriptions SHALL not
affect generated partners bytes.

#### Scenario: An unrelated operation changes
- **WHEN** another OpenAPI path or the shared top-level description changes
- **THEN** partners projection hash and generated files SHALL remain unchanged

### Requirement: Partners success SHALL expose one authoritative selected metric scale

The authoritative `contracts/schemas/partners/success-envelope-v1.schema.json` SHALL require `data.metricScale` in both success scopes. Global SHALL reference the existing rankings GlobalRankingsMetricScaleV1; personal SHALL reference RankingsMetricScaleV1. The shape SHALL be `{metric, kind:"linear", max}` with the existing count/integer-hundredths/exact-Rational discriminators and nullable maximum semantics. No independent copied scale definition or browser-computed substitute SHALL become authority.

The metric SHALL equal the normalized requested view sort, defaulting to count. Global responses SHALL exclude preference scales. A valid zero SHALL remain distinct from null absence. All other partners request, item, leader, pagination, metadata and error semantics SHALL remain unchanged. The Backend is the producer and the generated Go/TypeScript models plus frontend adapter are consumers.

#### Scenario: A personal preference page is returned
- **WHEN** a personal request uses preference sort
- **THEN** metricScale SHALL contain metric preference, kind linear and either the exact nonnegative absolute-maximum Rational or null
- **AND** row scores and leader scores SHALL retain their original signs

#### Scenario: Global or malformed scale is returned
- **WHEN** a global response supplies a preference scale, any response omits metricScale, or its metric/max union is invalid
- **THEN** strict contract validation SHALL reject the response without defaulting or dropping fields

#### Scenario: A zero differs from unavailable evidence
- **WHEN** all available preference scores are valid zero
- **THEN** the scale maximum SHALL be Rational 0/1
- **AND** no usable scores SHALL instead yield null

### Requirement: Partner scale evidence SHALL remain isolated and cross-language

Existing partners case files SHALL contain bounded evidence for off-page negative absolute maxima, ordinary maxima, empty/all-missing/all-zero populations and stable view changes. The Node verifier SHALL load the transitive existing rankings definitions, reject malformed/scope-invalid scales and verify declared metric consistency. Partners Go and TypeScript generation SHALL retain its existing isolated projection and regenerate every affected owned output; generated bytes SHALL never be hand-edited. Ranking and unrelated operation schemas/goldens/generated bytes SHALL remain unchanged.

#### Scenario: The largest magnitude is not a positive leader
- **WHEN** a complete-set example has preference leader +1/5 and an off-page -4/5 partner
- **THEN** the accepted selected scale SHALL be 4/5 even on the page containing only the +1/5 partner
- **AND** typed Go and TypeScript round-trip SHALL preserve its exact numerator and denominator

#### Scenario: An unrelated operation changes
- **WHEN** an unrelated OpenAPI path or description is varied
- **THEN** partners projection isolation SHALL still hold and unrelated generated consumers SHALL not be rewritten by this change
