## Requirements
### Requirement: Candidates contract SHALL separate input, view, and frontend state

The candidates request SHALL be a closed object containing required `query`,
required `input.positionKey`, optional `view`, and optional
`refreshCollection`. `input.positionKey` SHALL be one of the ordered submitted
query positions. Search, sort, order, page, and pageSize SHALL be view fields.
Selected state, alternate identities, query revision, request ID, data version,
theme, image URL, and work lists SHALL NOT be request or response fields.

Personal scope SHALL allow `count`, `average`, and `globalAverage`; global scope
SHALL allow only `count` and `average`. Collection refresh SHALL be accepted
only for personal scope.

#### Scenario: Current position is omitted or unknown
- **WHEN** input positionKey is absent or is not a member of query.positionKeys
- **THEN** the request SHALL fail with `FIELD_INVALID` at `/input/positionKey`

#### Scenario: Frontend selection is supplied
- **WHEN** a request or response contains selected-person state
- **THEN** the closed contract SHALL reject it

### Requirement: Candidates response SHALL keep complete counts distinct from view totals

The success response SHALL carry ordered `positionCounts` for every submitted
query position, where each count is the complete unsearched unique-person
count for that position. It SHALL separately carry the current position,
workUnit, ranked current-position items, and pagination total after current
search. Each item SHALL contain the backend rank, `{id,name,nameCN}` person
reference, and subject/series `workCount`.

Ranks SHALL be assigned from the complete sorted current-position set before
search and pagination. Position counts SHALL not change with current position,
search, sort, order, page, or pageSize.

#### Scenario: Search matches rank gaps
- **WHEN** current-position search retains complete ranks 2 and 8
- **THEN** items SHALL retain ranks 2 and 8, pagination total SHALL be 2, and every position count SHALL remain unchanged

#### Scenario: Page is beyond the searched list
- **WHEN** a valid page begins after the searched candidates
- **THEN** the endpoint SHALL return 200 with empty items, unchanged position counts, and the searched total

### Requirement: Candidate wire generation SHALL be capability isolated

The repository SHALL contain deterministic global/personal/error goldens
consumed by Go and TypeScript checks. Candidate generators SHALL hash and
generate from only `/candidates` and its transitive owned component graph.

#### Scenario: Candidate generation is repeated
- **WHEN** Go and TypeScript generators run twice from identical inputs
- **THEN** candidate inventories and bytes SHALL be identical and accepted query, catalog, and rankings generated bytes SHALL remain unchanged
