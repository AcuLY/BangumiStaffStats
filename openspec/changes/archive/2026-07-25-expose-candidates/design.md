## Contract

`POST /api/v1/candidates` accepts
`{query,input:{positionKey},view?,refreshCollection?}`. `positionKey` must be
one member of the submitted ordered `query.positionKeys`; the server never
silently substitutes the first position. View defaults are empty search,
`count`, descending, page 1, and pageSize 10.

Personal sort values are `count`, `average`, and `globalAverage`; global sort
values are `count` and `average`. Explicit collection refresh is valid only for
personal scope. The success envelope carries:

- complete unsearched unique-person counts for every query position in query
  order;
- the current position and work unit;
- current-position rows containing server rank, person reference, and
  subject/series work count;
- searched pagination total;
- request/data version and personal collection freshness metadata.

No selected flag, alternate identity, work list, image URL, or frontend state
crosses the wire.

## Computation

The service normalizes one shared query, evaluates each position independently
against the same filtered Archive/collection evidence, derives immutable
statistics needed for sorting, and records complete counts before search.
Within the requested position it applies the accepted strict total order,
assigns ranks before search, then searches and paginates. Missing metrics remain
last in both directions and stable person ID is the final tie-breaker.

The expensive core is cached by operation, dataVersion, queryDigest,
position-input digest, and collection digest only for personal scope. Search,
sort, order, and pagination are projections and never enter the result key.
Cache hit/miss/oversize outcomes do not alter the response.

## Integration

Candidate generation selects and hashes only the `/candidates` operation and
its transitive component graph. Existing query, catalog, and rankings
projections and generated bytes remain unchanged. The handler reuses the
result-operation no-store/error family, strict body/parameter limits,
cancellation, request IDs, readiness, and typed collection failures.

During concurrent implementation, new candidate-owned paths may land early;
shared OpenAPI and runtime registry edits wait until the rankings implementation
has been committed and handed off.

## Verification

Goldens and Go tests cover personal/global sorts, ordered position counts,
independent per-position membership, rank-before-search, empty and out-of-range
pages, missing metrics, series counts, stale collection, refresh restrictions,
unknown/current position validation, cancellation, cache immutability, and
strict transport/error mapping.
