## Context

Development acceptance successfully admitted the candidate, artifacts,
official Archive, toolchains, and sealed caches, then routed one failure to
`owner.contracts`: Catalog code generation created a temporary module requiring
only `oapi-codegen/runtime v1.1.2`, so minimal version selection requested its
unsealed `google/uuid v1.5.0` dependency. The accepted Backend closure already
locks `google/uuid v1.6.0`.

Separately, Archive manifests include domain/cast rule tokens in dataVersion,
but the compatibility matrix and consumers do not restrict them. Formal
production output uses `domain-raw-v1` and `cast-exact-v1`, while older minimal
contract fixtures still say `domain-v1`. Component evidence also lacks a
whole-application version.

## Goals / Non-Goals

Goals:

- close every temporary Go build over exact admitted module versions;
- establish one production Archive rule pair and reject all other pairs;
- propagate rule and `v0.1.0` identities from Contracts through runtime and
  immutable artifacts;
- provide inspectable Backend binary identity;
- preserve all frontend presentation and interaction behavior.

Non-goals:

- no statistical, query, API wire, SQLite DDL, UI, or interaction change;
- no new dependency and no network-enabled acceptance;
- no release publication, tag, deployment, activation, or host mutation.

## Decisions

### Catalog compilation uses the accepted higher module version

The temporary compile module SHALL explicitly require both
`github.com/oapi-codegen/runtime v1.1.2` and
`github.com/google/uuid v1.6.0`. The generation evidence SHALL declare this
closed ordered requirement set. This matches the admitted Backend Go closure,
keeps minimal version selection deterministic, and avoids adding a second
cache authority.

Alternatives rejected:

- adding `uuid v1.5.0` only to the acceptance cache would hide a product owner
  gate that is not independently offline-reproducible;
- enabling public Go proxy access would violate the owner gate;
- vendoring generated dependencies would add unnecessary duplicated source.

### One production Archive rule tuple

The compatibility matrix's only supported tuple SHALL include
`domainRulesVersion=domain-raw-v1` and
`castRulesVersion=cast-exact-v1`. Existing minimal/vectors and their derived
SQLite/manifest/pointer/index bytes SHALL be regenerated by the established
bounded fixture tooling. Updater construction SHALL use constants rather than
caller-controlled request values; Backend SHALL compare the manifest to the
matrix tuple before recomputing dataVersion or opening SQLite.

This makes the already-implemented formal producer the authority and removes
the ambiguous older `domain-v1` label.

### Root VERSION is whole-application authority

`/VERSION` SHALL contain exactly `v0.1.0` plus LF. It is distinct from language
package versions. Each component statement SHALL carry the same application
version, and the final compatibility manifest SHALL reject disagreement.

Backend builds SHALL inject `Version` and `Commit` into a small
`internal/releaseinfo` package for both `bgmss-api` and `archive-smoke`.
Development source execution may report `dev`/`unknown`; distributable
artifacts must report `v0.1.0` and their exact 40-hex revision. API startup
passes the same identity to existing observability metadata. The
`archive-smoke --build-info` mode emits only canonical inspection JSON and is
mutually exclusive with Archive validation flags; normal validation output
remains byte-for-byte governed by its existing contract.

OCI labels, bundle metadata, component statements, and SPDX package
`versionInfo` SHALL agree. Updater and Frontend artifacts bind the same root
version without changing Python package semantics or frontend runtime/UI.

### Artifact schemas remain pre-release v1 with a closed required extension

The development-only statement and compatibility schemas have not been
released. They SHALL retain schemaVersion 1 while adding required
`applicationVersion`, exact Archive rule fields, and the compatibility-matrix
digest, and all positive/negative fixtures and validators SHALL change
atomically. This avoids maintaining an unused legacy schema before the first
application release.

## Risks / Trade-offs

- [Fixture regeneration changes many binary/digest files] → use only the
  existing bounded generator, then verify closed inventories and language
  consumers independently.
- [Build identity changes reproducible artifact bytes] → inject only canonical
  version/revision, use the existing source epoch, and compare two fresh builds.
- [Component blocks touch shared Contracts inputs] → Contracts lands the
  authority first; Backend and Updater/Frontend consume it without editing the
  same files.
- [A version appears in user-visible frontend bytes] → bind it to build
  metadata/evidence only; do not add UI markup, copy, or behavior.
