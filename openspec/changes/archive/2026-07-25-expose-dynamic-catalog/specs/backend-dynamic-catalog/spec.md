## ADDED Requirements

### Requirement: Apply SHALL preserve dependency and owner boundaries

Before any write, the Backend owner SHALL prove that the three exact
dependencies have exited; the Contracts block is main-agent accepted with
exact OpenAPI/index/case hashes; the Git index is empty; allowed dirty paths
and HEAD are recorded; and no active owner overlaps the exact writable set.
Backend SHALL consume Contracts and `archive.Store` read-only and SHALL not
copy shared schemas/goldens, edit Archive internals, broaden package
dependencies, or add a module. The existing query-wire projection SHALL be
adapted only to select its already accepted empty-path/query-component subset
from the now larger OpenAPI document; its generated bytes and declaration
inventory SHALL remain unchanged.

#### Scenario: Handoff and workspace are exact
- **WHEN** dependency, Contracts, index, dirty-path, and owner-envelope checks all match
- **THEN** the Backend owner MAY create one unstaged implementation candidate in its exact paths

#### Scenario: A prerequisite or boundary differs
- **WHEN** a dependency is active, a contract hash differs, the index is nonempty, paths overlap, or a protected edit/dependency is needed
- **THEN** apply SHALL stop before mutation
- **AND** it SHALL not clean, reset, reinterpret, or broaden another owner's work

#### Scenario: The shared OpenAPI gains the catalog operation
- **WHEN** the existing query-wire generator reads the accepted larger OpenAPI
- **THEN** its owned projection SHALL still contain exactly the previously accepted query components and empty paths
- **AND** `query_wire.gen.go` SHALL remain byte-identical

### Requirement: The backend SHALL project catalog data only through the read-only Store

The catalog package SHALL accept a request context and a currently published
`archive.Store` interface exposing only identity and bounded read queries. It
SHALL execute fixed parameter-free `SELECT` statements against exactly
`catalog_position`, `catalog_position_member`, `catalog_group`,
`catalog_group_member`, `catalog_capability`, and
`catalog_selection_rule`, using `staff_position.categories` only where the
accepted API contract requires category metadata. It SHALL not open SQLite,
read pointer/manifest/filesystem paths, retain raw row handles, issue writes,
or access updater configuration/runtime code.

Because the Store is immutable, separately executed reads SHALL share one
validated snapshot identity. Every rows lifetime SHALL close on success,
error, or cancellation. Context cancellation/deadline SHALL terminate reads
and prevent response publication. The package SHALL return a newly owned
immutable value that handlers cannot mutate across requests; it SHALL retain
no global mutable cache in this change.

#### Scenario: A published snapshot is read
- **WHEN** the fixed Store queries return one valid accepted catalog
- **THEN** all rows SHALL be closed and one immutable projection with the exact Store dataVersion SHALL be returned
- **AND** no filesystem, pointer, manifest, updater, or mutation API SHALL be used

#### Scenario: Reading is canceled or fails
- **WHEN** context cancellation, query failure, scan failure, rows error, or close-sensitive failure occurs
- **THEN** all acquired rows SHALL close and no catalog value SHALL publish
- **AND** the prior Store and all Archive bytes SHALL remain unchanged

### Requirement: Store rows SHALL be validated and projected deterministically

The Backend projection SHALL implement the exact Contracts catalog wire and
ordering without a static position-key/name/category enum. It SHALL validate
every PositionKey grammar, subject type, kind-specific field, localized name,
display order, selectable status, capability, rule, group, member, category,
exclusive identity, and referential/uniqueness invariant before returning any
data. It SHALL derive only wire presentation fields explicitly specified by
Contracts, such as kind-specific fields or status from accepted row columns;
it SHALL not infer capability, grouping, cast, staff-set membership, or
business meaning from a key prefix or label.

Subject types, positions, groups, members, categories, capabilities, rules,
and memberKeys SHALL use the exact Contracts order. Unknown raw staff credits
and unresolved position IDs are absent from the catalog tables and SHALL not
be queried or fabricated. Hidden positions SHALL never appear in a selectable
group. Empty but valid groups SHALL follow the Contracts policy rather than
being silently removed.

#### Scenario: Identical Stores are requested repeatedly
- **WHEN** the same immutable Store is projected under different request IDs
- **THEN** the data and dataVersion bytes SHALL be identical and only request ID may differ

#### Scenario: A row is unknown or contradictory
- **WHEN** a row has an unknown enum/value, duplicate identity, dangling or cross-type reference, illegal order/name/key, hidden selectable reference, or contradictory rule/capability
- **THEN** the complete projection SHALL fail as an internal contract error
- **AND** no row SHALL be skipped, normalized privately, or returned partially

### Requirement: Dynamic and dormant positions SHALL require no handler enum

Every accepted common exact position SHALL flow from Store rows to the wire,
including positions with no credits and future valid additions. The four
accepted anime/game cast positions SHALL retain exact main/all scope and
exclusive identities; official common positions 101–106 SHALL remain staff.
No cast position may be synthesized for book/music/real.

The current empty staff-set tables SHALL produce no staff-set wire objects.
The Backend test corpus SHALL then use the Contracts synthetic valid staff set
to prove that one `staffSet` entity, sorted members, conservative
capabilities, custom-group reference, and union rule pass through the same
generic projection without a new route branch, static key, or type change.

#### Scenario: Common adds a valid position
- **WHEN** a valid Store adds one accepted common-backed position and its rows
- **THEN** the next response SHALL contain that position without a Go enum/source edit
- **AND** all existing identities and ordering rules SHALL remain stable

#### Scenario: Active staff sets remain empty
- **WHEN** the current accepted snapshot contains zero staff sets
- **THEN** the response SHALL contain no staff-set object/reference/rule
- **AND** it SHALL not inspect legacy mappings or synthesize an empty placeholder

### Requirement: The exact HTTP route SHALL preserve accepted transport behavior

The runtime SHALL register exactly `GET /api/v1/catalog`. A valid request SHALL
return the generated strict success envelope with `Content-Type:
application/json`, `Cache-Control: no-cache`, generated `X-Request-ID`,
matching `meta.requestId`, and exact Store `meta.dataVersion`. It SHALL accept
no query or body. Wrong method SHALL return 405 `INVALID_REQUEST` and exact
`Allow: GET`; a query or non-empty body SHALL return 400 `INVALID_REQUEST`.

If no Store is published, the route SHALL return 503 `NOT_READY`. Invalid
Store domain data or an unexpected read/encode failure SHALL return sanitized
500 `INTERNAL_ERROR`. The accepted deadline middleware SHALL return 504
`UPSTREAM_TIMEOUT` only before commit, while client/process cancellation
before commit writes nothing. All errors SHALL be `no-store`, carry the same
generated request ID, omit dataVersion, and expose no SQL, row, Archive path,
raw error, or catalog content. Encoding SHALL complete before commit so a
failure cannot leave valid-looking truncated JSON.

#### Scenario: Catalog succeeds
- **WHEN** a valid input-free GET reaches a published valid Store
- **THEN** one strict 200 no-cache envelope SHALL be committed with matching request ID and dataVersion

#### Scenario: Catalog is not ready or invalid
- **WHEN** Store publication is absent, domain rows are invalid, or encoding fails before commit
- **THEN** one 503 or 500 no-store envelope SHALL be returned without dataVersion or partial data

#### Scenario: Cancellation wins
- **WHEN** deadline, client cancellation, or shutdown wins before or after response commit
- **THEN** the accepted middleware outcome and single-commit rules SHALL hold
- **AND** no goroutine, rows lifetime, or second response SHALL remain

### Requirement: Runtime composition and observability SHALL remain bounded

Application composition SHALL inject only a read-only current-Store provider
into the catalog handler and SHALL preserve liveness, readiness, metrics,
image, startup-failure, and shutdown behavior. On startup Archive load
failure, the catalog route MAY remain registered but SHALL return
`NOT_READY`; it SHALL never trigger retry, fallback, reload, or another Store
selection.

Every catalog request SHALL map to the closed `catalog` route and operation
metric labels. One typed business request SHALL emit exactly one mutually
exclusive `query_completed` or `query_rejected` terminal event when a JSON
terminal response is produced; cancellation before commit emits neither.
Events and metrics SHALL contain only the accepted bounded facts and SHALL not
contain dataVersion, position/group/rule/capability values, row counts, SQL,
query string, request body, or raw error. No new metric family, arbitrary
label, dashboard, or external sink is admitted.

#### Scenario: Catalog traffic is observed
- **WHEN** valid, rejected, not-ready, internal-error, timeout, and canceled catalog requests run concurrently with metric scrapes
- **THEN** terminal-event cardinality, route/operation labels, status/outcome metrics, and cancellation semantics SHALL match the closed contract
- **AND** no catalog data or Archive identity SHALL enter event payloads or labels

#### Scenario: Archive startup failed
- **WHEN** the accepted startup loader fails and the degraded HTTP runtime serves
- **THEN** health/image/metrics retain their accepted behavior and catalog returns `NOT_READY`
- **AND** no catalog Store read, reload, fallback, or synthetic empty success SHALL occur

### Requirement: Acceptance SHALL prove cross-language parity and preserve scope

Backend tests SHALL consume every catalog API golden, compile the generated
wire, compare logical Store rows to exact response values, and cover all five
types, dynamic/no-credit positions, group duplication/order/fallback,
main/all, official 101–106, empty/synthetic staff sets, capability matrices,
unknown/corrupt rows, method/query/body/not-ready/error/deadline/cancel,
single commit, terminal event, metric cardinality, deterministic replay, and
rows cleanup. Fuzz/property tests SHALL target domain-row validation,
reference graphs, HTTP input rejection, and JSON encoding boundaries.

Acceptance SHALL run the exact generation `--check`, targeted/full Go tests,
race, vet/static checks, build, architecture route/dependency inventory,
OpenAPI/golden verifier, strict change/all validation, doctor, diff check, and
physical/index residue checks. No API beyond catalog and no UI/query result/
cache/collection/updater/operations result may be claimed.

#### Scenario: Development candidate passes
- **WHEN** every contract, unit, property/fuzz, race, generation, architecture, build, OpenSpec, inventory, and residue gate passes
- **THEN** Backend MAY hand one unstaged local catalog implementation to main-agent review
- **AND** it SHALL not claim commit, push, release, deploy, activation, UI, statistics, or production completion

#### Scenario: Any gate fails
- **WHEN** one contract, race, generation, route, dependency, protected-path, inventory, or residue gate fails
- **THEN** handoff SHALL stop with bounded evidence and no partial claim
- **AND** protected files, refs, prior snapshots, and external state SHALL remain unchanged
