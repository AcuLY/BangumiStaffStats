## MODIFIED Requirements

### Requirement: Candidates contract SHALL separate input, view, and frontend state

The candidates request SHALL be a closed object containing required `query`,
required `input.positionKey` whose value is either null or a canonical string,
optional `view`, and optional `refreshCollection`. Null SHALL request all
ordered query positions; a string SHALL be one of the ordered submitted query
positions. Search, sort, order, page, and pageSize SHALL be view fields.
Selected state, query revision, request ID, data version, theme, image URL, and
work lists SHALL NOT be request fields.

Personal scope SHALL allow `count`, `average`, and `globalAverage`; global scope
SHALL allow only `count` and `average`. Collection refresh SHALL be accepted
only for personal scope.

#### Scenario: Current position is null
- **WHEN** input positionKey is null
- **THEN** the endpoint SHALL evaluate all query.positionKeys as one mixed person view

#### Scenario: Current position is unknown
- **WHEN** a non-null input positionKey is not a member of query.positionKeys
- **THEN** the request SHALL fail with `FIELD_INVALID` at `/input/positionKey`

#### Scenario: Frontend selection is supplied
- **WHEN** a request contains selected-person state
- **THEN** the closed contract SHALL reject it

### Requirement: Candidates response SHALL keep complete counts distinct from view totals

The success response SHALL carry ordered `positionCounts` for every submitted
query position, where each count is the complete unsearched unique-person count
for that position. It SHALL separately carry nullable current position,
workUnit, ranked items, and pagination total after current search. Each item
SHALL contain backend rank, `{id,name,nameCN}`, subject/series `workCount`, and
ordered non-empty `positionKeys` identifying that person's actual contributing
query positions. Single mode SHALL return exactly the current key per item; all
mode SHALL return all matching keys in query order and each person once.

Ranks SHALL be assigned from the complete sorted current person set before
search and pagination. Position counts SHALL not change with current position,
search, sort, order, page, or pageSize.

#### Scenario: All positions contain an overlapping person
- **WHEN** one person appears under two query positions in all mode
- **THEN** one item SHALL contain both ordered positionKeys and unioned workCount

#### Scenario: Search matches rank gaps
- **WHEN** current search retains complete ranks 2 and 8
- **THEN** items SHALL retain ranks 2 and 8 and counts SHALL remain unchanged

#### Scenario: Page is beyond the searched list
- **WHEN** a valid page begins after the searched candidates
- **THEN** the endpoint SHALL return 200 with empty items and unchanged counts

### Requirement: Candidate wire generation SHALL be capability isolated

The repository SHALL contain deterministic global/personal/error goldens
covering single and all mode, consumed by Go and TypeScript checks. Candidate
generators SHALL hash and generate from only `/candidates` and its transitive
owned component graph.

#### Scenario: Candidate generation is repeated
- **WHEN** Go and TypeScript generators run twice from identical inputs
- **THEN** candidate bytes SHALL be identical and unrelated generated bytes unchanged
